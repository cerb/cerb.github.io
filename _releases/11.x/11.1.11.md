# Changelog

## Added

* **[Data Queries/Tickets]** In `worklist.subtotals` data queries, `of:ticket` now supports `by:sender.first` and `by:sender.last`. These keys were suggested by autocompletion but returned an "Unknown by: field" error.

## Fixed

* **[Data Queries]** Fixed an issue with `worklist.subtotals` data queries when grouping time-series data by `@quarter` or `@quarterofyear` against a 'date' custom field.

* **[Mailboxes]** Fixed an issue with mailboxes where consecutive failure counts could exceed the field range of (0-127).

## Security

* **[Security/Dependencies]** Upgraded guzzlehttp/guzzle to 7.15.3 in response to a security advisory.

* **[Security/Dependencies]** Upgraded smarty/smarty to 4.5.7 in response to a security advisory.

* **[Security/Dependencies]** Upgraded league/commonmark to 2.10.0 in response to a security advisory.

* **[OAuth Apps/Security]** The OAuth2 authorization flow now returns to the hostname in `APP_HOSTNAME` after a worker signs in or grants consent. On instances where the server sees a different hostname than workers browse, clients no longer get bounced to that other address partway through the flow.
  
  When an authorization request reached `/oauth/authorize` and the worker still had to sign in or approve the requested scopes, Cerb saved the return address using the hostname from the incoming request instead of the one configured in `APP_HOSTNAME`. If a proxy or load balancer presents a hostname other than the one workers browse, the round trip came back on the wrong origin. Session cookies are scoped to a single hostname, so no session existed there, and the flow either looped back to the sign-in form or stopped with an access denied error. On Cerb Cloud this showed up as a custom domain falling back to the instance's `*.cerb.me` address.
  
  The final redirect that hands the authorization code back to the client was never involved. That has always been the client's own `redirect_uri`, or the Redirect URL stored on the OAuth app when the client omits it.
  
* **[OAuth/Security]** OAuth2 consent is now bound to the app and scopes it was granted for. An approval left behind by an abandoned authorization flow can no longer approve a different app in the same browser session.
  
  That state is reused for 20 minutes and, in the OAuth flow, is only cleared once an authorization request runs to completion. A flow abandoned after the consent screen -- the worker approves an app but the browser never makes it back to `/oauth/authorize` -- therefore leaves a granted consent sitting in the session. Within that window, following an authorization link for a second app issued it an authorization code with no consent screen shown, and the same gap let an app that had already been approved widen its scopes silently.
  
  The login state now records the `client_id` and the scope set that were displayed on the consent screen, and `/oauth/authorize` requires both to match the request in hand through `wasConsentAskedFor()`. Scope comparison ignores order and duplicates, so a reordered scope list does not force a redundant re-prompt. A declined request still counts as answered and continues to return `access_denied` to the client instead of looping back to the consent screen, and a POST to `/login/consent` with no authorization request pending now grants nothing.
